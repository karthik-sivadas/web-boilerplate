# Layered application and PostgreSQL research

Research retrieved **2026-09-05** from official documentation and exact published distributions. This document records evidence and decisions, not an assertion that all release gates passed. See [ADR 004](adr-004-layered-postgres.md) and the [acceptance checklist](tasks/layered-postgres.md). Earlier SQLite recommendations in ADR 002 and the architecture review are historical: the latest explicit user instruction selects PostgreSQL and full backend implementation.

## M2 implementation feedback

The approved split is now implemented: thin routes, scoped remote coordination, derived view models, forms/components/pages, fixed SSR/proxy transport, independent DTOs and inward-facing semantic transaction ports. Legacy browser writing/reset/memory fallback was replaced deliberately, not silently dropped; [verification mapping](postgres-verification.md) maps the preserved safety capabilities. StrictMode request scope replay is explicitly tested, and query identity includes user/session/epoch rather than callback objects.

Real browser/PostgreSQL testing found that pg returns BIGINT timestamps as strings while Better Auth rate limiting uses numeric addition. This produced absurd Retry-After values despite correct 429 enforcement. A pool-scoped, safe-integer parser restores numeric semantics without a global driver mutation or weakened limits. API tests now bound the actual auth retry window. Durable import-receipt lookup was added so a refresh or lost import response does not strand rollback metadata. Real cookie-switch tests prepare server-issued sessions before opening the stale tab's draft, isolating intent races from legitimate periodic reconciliation and auth-rate waits.

Separate source-free Docker targets, real PG restart/outage smoke and resolved-import consumer failure fixtures supply operational/dependency evidence beyond diagram or source-string checks. [Operations](postgres-operations.md) documents explicit migration and preservation boundaries; hosted deployment and independent review remain separate acceptance.

## PostgreSQL and authentication evidence

- [Better Auth PostgreSQL adapter](https://www.better-auth.com/docs/adapters/postgresql), [Hono integration](https://www.better-auth.com/docs/integrations/hono), and [published 1.7.3 distribution](https://registry.npmjs.org/better-auth/1.7.3): a `pg.Pool` selects the internal Kysely PostgreSQL dialect. No new ORM is necessary.
- Actual `getMigrations(authOptions)` output was generated against a newly owned random test schema and reviewed into `apps/api/migrations/001-auth.sql`. Physical tables are quoted `user`, `session`, `account`, `verification`, `rateLimit`; auth dates are `timestamptz`, but rate-limit `lastRequest` is bigint epoch milliseconds. `getMigrations` does not itself supply an advisory lock, application ledger, or atomic transaction. Runtime schema validation is introspection, not migration. Auth creation is lazy after readiness because failed schema checks can be cached.
- **Review-discovered sign-out nuance (Better Auth 1.7.3):** installed `dist/api/routes/sign-out.mjs` catches database deletion failures, clears cookies and returns success. A real PostgreSQL row-lock reproduction returned 200 before repair while DELETE was blocked. The narrow API wrapper now confirms the original cookie has no valid session through the read-only guard before forwarding sign-out success/cookies; still-valid or unverifiable revocation is sanitized 503 without cookie expiration. Public refresh and cookie parsing remain upstream-owned. Tests prove failed deletion and successful retry, not just total database outage.
- **Read-only guard nuance:** `disableRefresh` alone still permits deletion of expired sessions. The non-public guard uses `deferSessionRefresh:true`, GET, `disableRefresh:true`, and `disableCookieCache:true`. Its separate pool sets PostgreSQL `default_transaction_read_only=on`; valid/expired/revoked paths and unchanged session rows are tested. Public Better Auth handlers retain normal refresh behavior and opaque cookie handling. No custom cookie parser or HTTP identity header is an authority.
- [node-postgres pools](https://node-postgres.com/apis/pool) and [transactions](https://node-postgres.com/features/transactions): acquire one client, BEGIN/COMMIT/ROLLBACK on that client, release in finally. `pool.query('BEGIN')` is not a transaction across later pool calls. Bound acquisition, pool size, statements, locks, idle transactions and lifecycle. Driver errors must not be emitted to clients or logs with credentials/SQL.
- [PostgreSQL explicit locking](https://www.postgresql.org/docs/16/explicit-locking.html): owner-row locks serialize workspace changes; a repeatable-read transaction provides the canonical read snapshot. Migrations use a session advisory lock and ledger/checksum transaction on one checked-out client, never hold one pool's only client while asking that pool to plan migrations.
- PostgreSQL is **mandatory by user decision**, superseding the earlier single-instance SQLite recommendation. It adds service operations, credentials, backups and connection capacity planning, but supplies real shared transactional persistence and ownership constraints. New accounts start empty; there is no automatic seed or legacy migration.
- [PostgreSQL 16.11 release](https://www.postgresql.org/docs/16/release-16-11.html), [16.14 release](https://www.postgresql.org/docs/release/16.14/), and [official image metadata](https://registry.hub.docker.com/v2/repositories/library/postgres/tags/16.15): native 16.11 is outdated. Supervisor selected **16.15-bookworm**, digest `sha256:bb3e1a57e5407e0a5280b4211980a5e537f4abd234a87014ac979849a78dd825`. M1 uses that existing service only for owned test resources; it does not reconfigure or stop it.

## Session-intent binding discovered in foundation review

A cookie-authorized request can still carry the wrong tab's intent: tab A captures lease A, tab B switches the shared cookie to B, and A dispatches before broadcast/focus reconciliation. Query epoch keys alone cannot stop B data landing in A's request context or A's draft writing to empty workspace B at the same revision. Require the non-authoritative `X-Expected-Session-Id` precondition on every workspace operation. Verify the cookie first, compare the verified session ID second, reject missing/invalid binding with 400 and mismatch with `409 SESSION_CHANGED` before business access. This does not authorize by header or replace pre/post action leases. Genuine-cookie tests cover cross-account and same-user replacement; the controlled browser/proxy race remains M2.

## Preservation and remaining delivery

M1 intentionally leaves existing web browser persistence and SQLite auth code untouched so an incomplete frontend cutover cannot silently strand data. M2 must replace it with explicit remote state and a fixed same-origin proxy, and provide opt-in offline auth preservation using **synthetic fixtures only** during development. Never discover or read a real `.data`, `.env` or browser store. Auth IDs/password hashes/sessions must be preserved by the optional utility; importing an unrelated new PostgreSQL account does not recover old IDs. Browser import/export/receipt/rollback endpoints and UI are M2 requirements, not delivered merely by creating a receipt table.
